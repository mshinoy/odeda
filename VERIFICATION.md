## Dashboard render — what was actually seen

Chromium was already installed on this machine (`chromium-browser`, snap); nothing was
downloaded to run these. Each tab was loaded against a live uvicorn, the
post-JavaScript DOM was dumped, and screenshots were captured and **looked at**.

| Tab | Observed |
|---|---|
| `#routes` | 15 routes, 821 attempts, sortable table |
| `#routes/<id>` | Leaflet initialised (7 panes), **29 OpenStreetMap tiles loaded**, pace-coloured polyline drawn, colour-ramp legend, two segment charts with bars and lines |
| `#aggregate` | 6 uPlot canvases, headline tiles, year-over-year table with signed deltas, HR-zone bars, day/hour heatmap |
| `#gear` | 13 gear cards with mileage, wear bars and threshold warning states |
| `#activities/<id>` | Map with polyline, edit form generated from `/api/fields`, gear dropdowns per kind, HR and pace charts |
| `#settings` | Garmin connection form, backfill estimate (1 218 days, 7 486 requests, 1:14:51–3:07:08), watermark table |
| indoor activity | "No GPS in this activity — treadmill, turbo or a lost signal." Everything below still rendered. |

Screenshots are in [`docs/screenshots/`](docs/screenshots/), all of synthetic data.

Three bugs were found this way and fixed, which is the point of looking rather than
asserting:

1. Every new chart rendered blank — `baseOpts` already prepends the x-series, so the
   leading `{ label: ... }` gave each chart one more series than data array.
2. The segment profile had relative speed, gradient and heart rate on one y-axis; at
   a 120–180 bpm scale the percentages were a flat line. Split into two charts.
3. The activity-type `<select>` omitted any value not in its suggestion list, so a
   strength session displayed "running" — and pressing Save would have retyped it.

## What this transcript does **not** prove

Stated plainly, because the difference between "built" and "verified" matters.

**Not verified, because there were no credentials on this machine:**

- **No Garmin account was ever contacted.** `login`, the MFA exchange, and the live
  half of `sync` and `backfill` are unexercised against the real service. They are
  tested only through an injected fetcher against handcrafted payloads
  (`tests/test_backfill.py`, `tests/fixtures.py`). The endpoint paths in
  `ingest/connect.py` and `ingest/details.py` are hardcoded literals taken from
  garth's own usage; if Garmin has moved one, it will fail at the first request.
- **The details-payload parser has never seen a real Garmin response.** Its column
  names come from documented `metricDescriptors` keys, and it reads them by name with
  fallbacks — but the shape is an informed reconstruction, not something observed.
- **Rate-limit and 429 back-off behaviour is untested against the real service.** The
  code paths exist and are unit-tested; the actual thresholds are unknown.
- **The export-ZIP importer has never seen a real Garmin export.** It was tested
  against a ZIP built in `tests/test_ingest.py` from the layout Garmin documented as
  of 2026-09.
- **First-backfill duration for a real multi-year account is an estimate**, derived
  from the configured per-request delay. It could be several times longer.

**Verified, but with a caveat worth knowing:**

- **Map tiles.** Tiles were observed loading from OpenStreetMap (29 of them in one
  capture). Taking many screenshots in quick succession then produced *partially*
  loaded tile grids — OSM throttles, as their usage policy says it will. The map code
  is fine; the tile server is rate-limiting. A self-hoster pointing `GA_TILE_URL` at
  their own server will not see this.
- **The data throughout is synthetic**, from `garmin_analytics/seed/synthetic.py`. It
  is physiologically coupled by construction — an athlete model run forward day by
  day — but it is not real training, and the GPS routes are parametric squiggles
  anchored on Doha landmarks, not anyone's recorded movements.
- **Cross-architecture builds were not attempted.** The image was built and run on
  x86-64 only. Nothing in it is architecture-specific, but ARM is unverified.

**Not tested at all:**

- Long-running stability. The container has been up for minutes, not weeks.
- Concurrent use from several browsers at once.
- Behaviour when the SQLite database grows past a few hundred megabytes.
